A caution for anyone forking a public notebook: `kaggle kernels pull` returns the **latest version**, not necessarily the version that carries the displayed score. I forked judith007's 0.664 notebook this way. Its best-scoring version is version 2 of 6, which uses a Sinkhorn mix of 0.30 and a typography coefficient of 1.5. The code I pulled had 0.60 and 1.2. My fork scored 0.659; with version 2's two values it scored 0.663. Before forking, compare what you pulled against the scored version on the notebook page.

Once my ensemble came from public forks, CV stopped telling me which parts mattered. This is the workflow I use now. All numbers are from my own runs.

**1. Make submissions cheap**

The scoring rerun did not use my weekly GPU quota; only the commit run did (175 s used, both before and after a roughly 2 h scoring run). The public test has only 3 rows, so on the commit run I write a placeholder and skip the model cells:

```python
LIGHT = os.environ.get('KAGGLE_IS_COMPETITION_RERUN') is None and len(test) < 50
```

That cut my commit from about 1.8 h to 167 s. The rerun still runs everything: the full and light commits of the same pipeline both scored 0.617.

**2. Guard against what a light commit can't catch**

A light commit doesn't prove that the rerun will work. I lost submissions or GPU time to these:

- **Input paths:** a Kaggle Model doesn't keep the dataset's top folder name, so an upstream glob can miss your mirror. I now run a free CPU script of about 1 minute that checks every lookup first.
- **Docker image:** one upstream notebook pinned an image whose torch had no CUDA. The commit passed, then the reruns failed after 3 h. Add `assert torch.cuda.device_count() > 0` to the light path.
- **Optional parts:** give them a deadline, and treat a failure like a timeout by dropping the part. Never `assert returncode == 0`.
- **Slow loads:** `load_file` on LoRA adapters read from a Dataset mount took about 100 s each, against 24 s in the author's log. Copying the adapters to `/tmp` took 34 s and cut my main pipeline from 4,884 s to 2,866 s (author: 2,859 s), with identical predictions.

I put these guards into a small CPU notebook you can copy from, with sample output for each: [ntl-fork-guard-utility](https://www.kaggle.com/code/mizuno0522/ntl-fork-guard-utility).

**3. Measure parts by removing them**

I set one part's blend weight to 0 and submit it with a light commit, about 3 minutes of GPU per variant. Two results on a 0.638 base:

| Removed | Public LB | Delta |
|---|---|---|
| ATLAS (10% blend) | 0.629 | −0.009 |
| Sinkhorn balancing | 0.636 | −0.002 |

Across the 10 variants I tried, every removal lowered the score, and weak but different models mattered more than their solo CV suggested.

**Limits**

- It uses up submission slots, so I run 2–3 a day and keep a reserve.
- It measures only the public part of the test, and scores are rounded to 3 decimals, so I don't read much into a delta of 0.001–0.002.
- Parts can substitute for each other: two similar parts can each look small alone and large when removed together, so test groups too.
- Removing is not the mirror of adding. See my next post.
